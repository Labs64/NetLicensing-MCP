# Changelog

Release notes for each version are published on the [GitHub Releases page](https://github.com/Labs64/NetLicensing-MCP/releases).

## Unreleased

### Added

- README: a "Connect in 30 seconds" section near the top with one copy-paste snippet per client (Claude Code, VS Code, Cursor, Claude Desktop, Docker) and a demo-mode variant, and a "Client setup" section with the details: Claude Code scopes and remote HTTP (`--transport http --header`), a VS Code `.vscode/mcp.json` that asks for the key (`inputs`, `password: true`) and a remote HTTP entry, a Cursor install link (`cursor://anysphere.cursor-deeplink/mcp/install`) and `${env:...}` key, Claude Desktop config paths for macOS, Windows and Linux, JetBrains (Copilot `mcp.json` with `servers`) and other clients.
- `docs/EXAMPLES.md`: six vendor scenarios (first run in demo mode, launching a subscription product, a support ticket, a renewal sweep, a customer migration, offboarding) with example prompts and the tool calls they trigger, marked as illustrative. Linked from the README. `tests/test_examples_doc.py` checks that every tool, argument and prompt named there is registered.
- `tests/test_registry_metadata.py`: validates `server.json` (after the release workflow's `${VERSION}` substitution) against the MCP Registry schema and `glama.json` against Glama's schema (both vendored in `tests/fixtures/registry/`), and checks that the server name, title and description agree across `server.json`, the Dockerfile labels, the release workflow, the README and `pyproject.toml`.
- PyPI keywords `mcp-server` and `licensing-as-a-service`; classifiers `Topic :: Office/Business` and `Topic :: Scientific/Engineering :: Artificial Intelligence`.

- Six setup and troubleshooting prompt templates next to the five audit prompts (`prompts/setup.py`, `register_setup_prompts`): `setup_subscription_product` (`product_name`, `plans`), `setup_trial` (`product_number`, `trial_days`, default 14), `onboard_customer` (`customer_name`, `product_number`, optional `licensee_number`, `module_number`, `license_template_number`), `migrate_customer` (`from_licensee_number`, `to_licensee_number`), `troubleshoot_validation` (`licensee_number`, optional `product_number`, `product_module_number`) and `issue_api_key` (`purpose`). Each walks the assistant through the task with the exact tool names and arguments, previews before changes, asks for confirmation before writes, never deletes or cascades on its own, and shows a new API key or checkout URL only once. Prompt arguments carry descriptions and the prompts have titles. The server instructions mention them. A test checks that every tool and argument a prompt names exists in the tool registry.

- `GET /ready` readiness endpoint (HTTP mode, no API key needed): `200` `{"status": "ready", "server", "version", "checks": {"app", "upstream"}}` when the MCP endpoint is running and the NetLicensing API answers, otherwise `503` with `"status": "not_ready"` and a `reason`. The upstream check is one unauthenticated `GET` of `NETLICENSING_BASE_URL` (3-second timeout; any HTTP status counts as reachable; timeouts, connection and other transport/protocol errors, and a malformed URL count as unreachable), cached for 15 seconds (a failure for 5 seconds). The reply names only the API's host name, never a key or the upstream response. `GET /health` (liveness) is unchanged and stays the load balancer / container health check; `deploy/aws/README.md` explains which probe to use for what.
- `netlicensing_server_info` is now a first-run check. Besides `version`, `base_url` and `demo_mode` it returns `status` (`ok` / `warning` / `error`), `auth` (`configured`, `source`: `env` / `header` / `demo` / `none`, `valid`: `true` / `false` / `null`; never the key), `checks` (`[{name, ok, detail}]`), `warnings`, plain-language `next_steps`, `transport` (`stdio` / `http`), `toolsets`, `read_only` and `tool_count`. By default it makes one read-only API call (lists one product, 10-second timeout) to check that NetLicensing is reachable and accepts the key (`401` → `valid: false`; `403` → `valid: true` with a failed `permission` check and a warning, since NetLicensing answers `403` to a valid key whose role does not allow the operation; network error or timeout → `valid: null` and a failed `reachable` check); the new optional `check_connection=false` skips the call. Its description tells assistants to call it first when something fails. The README has a new "First run" section.
- The server instructions tell assistants to run `netlicensing_server_info` first when a tool fails with an authentication, connection or configuration error, or when the user asks whether the setup works.
- Paging hints on list results: besides `count` (items in this response) a list result now carries the paging data NetLicensing reports — `total`, `page` (0-based), `total_pages`, `has_more` and, when there is a next page, `page_size`. Paged list tools add `next_page_hint`, the JSON-quoted `filter` value that fetches the next page. Fields the API does not send are left out; payment methods, licensing models, license types and countries are not paged.
- `netlicensing_list_bundles` accepts an optional `filter` (e.g. `active=true`, or `page=1;items=100` for the next page), like the other list tools.
- Error results now say what to do next: besides `error`, `status` and `detail` they carry `hint` (one actionable sentence), `suggested_actions` (names of registered tools, e.g. `netlicensing_list_licensees` when a licensee was not found) and `retryable` (`true` for 429, 5xx, timeouts and unreachable API; `retry_after_seconds` from `Retry-After` on 429). A missing entity (NetLicensing answers `400` `NotFoundException`), a duplicate number, a delete blocked by dependents, bad credentials, a too-low key role and a feature outside the pricing plan each get their own hint. Rejected confirmation tokens point at the matching `preview_*` tool. Hints never contain the API key, the `detail` text or more of the base URL than its host.
- `MCP_TOOLSETS` (comma list of toolsets: `products`, `bundles`, `modules`, `templates`, `licensees`, `licenses`, `tokens`, `transactions`, `payments`, `system`, `workflows`; default `all`) and `MCP_READ_ONLY=true` (only tools annotated read-only) shrink the registered tool list. `netlicensing_server_info` is always registered, and the server instructions mention an active restriction. Without these variables all 61 tools are registered as before.
- Structured tool output: every tool result now carries `structuredContent` (the same JSON object as the text content; non-object results as `{"result": ...}`), every tool declares an `outputSchema`, and error results set `isError`. The text content is unchanged.
- `docs/TOOLS.md`: a reference of every tool (title, read-only / write / destructive badge, annotations, description and parameters with type, required flag, default and description) and every prompt (with its arguments), generated from the server's registry by `scripts/gen_tools_doc.py`. The README's tool tables (folded per toolset), prompt tables and its tool and prompt counts are generated by the same script; the README also lists an example invocation per prompt. `python scripts/gen_tools_doc.py --check` (also a CI step and a test) fails when they are out of date.
- Deploy lint workflow (`.github/workflows/netlicensing-deploy-lint.yml`), run on pushes and pull requests to `master` that touch `deploy/**`, `Dockerfile`, `healthcheck.py`, `pyproject.toml`, `uv.lock`, `src/**` or the workflow itself (the image is built from the package and its lock file): `cfn-lint` (pinned to 1.61.0) on `deploy/aws/*.yaml`, `shellcheck deploy/aws/deploy.sh`, `deploy.sh help` without AWS credentials, and a Docker build of the release wheel that is started in HTTP mode and must turn healthy, answer `/health` and reject `POST /mcp` without a key with `401`. The App Runner template ignores cfn-lint's `W3697` (App Runner is in maintenance mode) in its two App Runner resources' `Metadata`; CONTRIBUTING.md shows how to run the checks locally.
- `tests/test_http_e2e.py`: end-to-end tests over the real HTTP app (`build_http_app()`) with a fake NetLicensing API: `/health`, `/ready` (upstream reachable and unreachable), `401` + `WWW-Authenticate` without a key, `initialize` with the `X-NetLicensing-API-Key` header or a Bearer token, `tools/list` (61 tools), a `tools/call` returning the response envelope, and per-request API keys, including two concurrent requests with different keys.

### Fixed

- `server.json` did not pass the MCP Registry schema: its `description` was longer than the 100 characters allowed, and with the declared `2025-09-29` schema the OCI package also needed a `version`. It now targets the current schema `2025-12-11`, uses `isRequired` instead of `required` for environment variables (the schema has no `required` there, and the registry drops unknown keys: the published 1.0.1 entry has no `required`, `homepage` or `license`), so `NETLICENSING_API_KEY` is now marked required for registry clients; it also adds `format` (`boolean`, `number`), `choices` for `MCP_TRANSPORT` and a `runtimeHint` (`uvx`, `docker`) per package, and drops the `homepage` and `license` keys, which the schema does not define (`websiteUrl` and `repository` stay). The `${VERSION}` placeholders and their substitution in the release workflow are unchanged.
- The published Docker image's title, description and url labels came from the GitHub repository (set by `docker/metadata-action`), not from the Dockerfile. The release workflow now passes the Dockerfile's values; the image title is "NetLicensing MCP Server" and its description matches `server.json`.
- README: the Docker HTTP example now sets `MCP_HOST=0.0.0.0`; without it the server listens on `127.0.0.1` inside the container and the published port does not answer. The Claude Desktop "HTTP mode" example, which started a detached container as if it were a stdio server, is removed (Claude Desktop's documented custom-connector flow takes a URL and has no custom headers; use stdio). The VS Code section no longer refers to a `.vscode/mcp.json` in the repository (it was deleted), and the JetBrains section shows Copilot's `servers` format instead of pointing to the `mcpServers` block.

- `initialize` reported the MCP SDK version as `serverInfo.version`; it now reports the netlicensing-mcp version.
- The audit prompts (`audit_full`, `audit_customer`, `audit_expiry`, `audit_cleanup`, `audit_anomaly`) were delivered to clients as a JSON dump of the message object (`{"role": "user", "content": {"type": "text", "text": "..."}}` with escaped newlines) instead of the prompt text. They now send the prompt text itself; the text is unchanged.

### Changed

- The title of `netlicensing_create_api_token` is now "Create API token" (was "Create api token").
- Prompt descriptions say more about what each prompt does (for example that `audit_expiry` generates renewal URLs and `setup_trial` creates a free, automatic TIMEVOLUME trial template and a FEATURE full-version template). Prompt names and arguments are unchanged.
- `netlicensing_server_info` makes one API call by default (see Added); pass `check_connection=false` for the previous no-call behaviour.
- `structuredContent` used to be the JSON *string* wrapped as `{"result": "..."}` (the MCP SDK default for tools that return `str`); it is now the parsed object. Error results (`{"error": true, ...}`) used to be sent with `isError: false`.

### Security

- Deleting a token no longer echoes the token number in full. For APIKEY tokens the number is the API key, for SHOP tokens the checkout credential; `get_token` / `list_tokens` already masked it, but the delete preview's `target` (`netlicensing_preview_delete_token`, and `netlicensing_delete_token` without `confirm_token`), the delete message (`Token <number> deleted (HTTP …)`) and the error for a confirmation token issued for another target showed it. They now show the read-path mask (`a1b****7890`; numbers under 16 characters become `****`) for every token type, since the type is not known on the delete and error paths without another API call. The confirmation token is still bound to the real token number. The `issue_api_key` prompt's revoke step now says these results show the key only masked.
- Logs no longer contain full token numbers. `httpx` logged every request URL at INFO, the default level (`HTTP Request: GET https://…/token/<number> …`), so reading, previewing or deleting an APIKEY or SHOP token wrote the key to stderr; in verbose mode `httpcore` added request details and `sse_starlette` logged every HTTP-mode response chunk, including a key shown once by `create_api_token`. These three loggers are now held at `WARNING` in every mode, verbose included. The server's own request lines (`GET …/token/**** …`) still show requests in verbose mode. The README and SECURITY.md now say that verbose mode also enables the MCP SDK's and web server's own DEBUG output, which is not redacted, and is for local debugging only.
